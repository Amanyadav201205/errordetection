● EXECUTIVE SUMMARY

Project Motivation, Problem Statement & Objectives

Bridging theoretical Data Link Layer error control with realistic physical channel noise modeling

1. The Physical Channel Problem Statement

Transmission media impairments and silent data corruption:

In modern digital communications, physical transmission media—including copper unshielded twisted pair (UTP), coaxial cabling, optical fiber wave-guides, and free-space radio frequency (RF) channels—are continuously subjected to environmental physical noise. Thermal noise generated by electron agitation, electromagnetic interference (EMI) from industrial machinery, signal attenuation over distance, cross-talk between adjacent conductors, and transient voltage spikes induce unpredictable bit inversions (logic 0 flipping to logic 1 or vice-versa) as well as multi-bit burst corruptions across physical lines.

In the absence of robust Data Link Layer error detection and correction mechanisms, corrupted bit patterns traverse silently into higher-layer protocols. This leads to severe data integrity failures, silent file corruptions, application crashes, and compromised cryptographic handshakes. Preventing silent data corruption requires mathematically sound redundancy techniques that detect and resolve frame errors before handing payloads to upper layers.

2. Pedagogical Gaps & Project Engineering Goals

Comprehensive interactive simulation suite and goals:

Traditional academic curricula in computer networks frequently treat error control algorithms as static textbook equations, divorcing the discrete mathematics of check bits from the dynamic reality of packet transmission across physical links. Students compute parities and remainders by hand on paper, but rarely observe how these redundant bits interact with transmission queues, propagation delays, and stochastic packet drop events across simulated networks.

To resolve this pedagogical limitation, our primary engineering objective was to construct an interactive, dual-mode simulation environment that pairs first-principles mathematical encoding with an authentic discrete-event network simulator (NS-2). The platform empowers users to inject arbitrary noise patterns, observe real-time syndrome calculations, and analyze packet traces across realistic communication channels.

● SYSTEM ARCHITECTURE

End-to-End Network Transmission Pipeline

The 6 architectural stages modeling sender encoding, channel transmission, noise, and receiver recovery

Transmitter Pipeline & Channel Traversal (Stages 1–3)

Message generation, mathematical encoding, and NS-2 link traversal:

The simulation architecture models the complete lifecycle of a network frame across six sequential pipeline stages. In STAGE 1 (Binary Data Ingestion & Validation), source messages are entered as arbitrary binary vectors or converted from ASCII plaintext, supporting 4-bit, 8-bit, 12-bit, and 16-bit presets alongside custom input lengths. In STAGE 2 (Redundancy Generation & Codeword Framing), the selected mathematical algorithm computes redundant check bits—such as parity bits, checksum words, or CRC remainder polynomials—and appends them to form the transmitted codeword.

In STAGE 3 (Physical Channel & NS-2 Modeling), the generated codeword is packetized and transmitted across a simulated point-to-point duplex link modeled in Network Simulator 2 (network_error_sim.tcl). The link is configured with 2.0 Mbps bandwidth, 10 ms propagation delay, and DropTail queue management, capturing link traversal latency and queue dynamics.

Noise Injection, Receiver Verification & FEC (Stages 4–6)

Physical corruption, syndrome decoding, and autonomous error recovery:

In STAGE 4 (Physical Noise & Error Injection), channel impairments are simulated either stochastically via the NS-2 ErrorModel or interactively by clicking individual bits on the simulator track to toggle them (0 ↔ 1), injecting random noise, or triggering 3-bit burst corruptions.

In STAGE 5 (Receiver Verification & Syndrome Computation), the receiving node recalculates check bits on the incoming frame, evaluating parity equations, 1's complement additions, or Modulo-2 polynomial long divisions. Finally, in STAGE 6 (Diagnostic Analysis, FEC & Decision), the system localizes bit errors, applies automatic Forward Error Correction (FEC) where algebraically possible (in 2D Parity and Hamming Codes), or triggers packet discard flags, displaying comprehensive step-by-step diagnostic feedback.

● ALGORITHM 1 OF 5: PART A

1D Parity Check: Theory & Mathematical Formulation

Minimal bandwidth redundancy mechanism for single-bit error detection

Parity Generation & Algebraic Principles

Mathematical definition, XOR trees, and decision boundaries:

One-Dimensional (1D) Parity Check, historically designated as Vertical Redundancy Check (VRC), represents the most lightweight and computationally inexpensive error detection mechanism in digital communication. The algorithm appends a single redundant parity bit (P) to an n-bit binary data stream so that the total count of 1-bits satisfies a pre-agreed parity convention. Under Even Parity, the check bit is generated as the Exclusive-OR (XOR) sum of all message bits: P = b₁ ⊕ b₂ ⊕ ... ⊕ bₙ, guaranteeing that the total count of 1s in the transmitted codeword is always an even integer. Under Odd Parity, P is inverted so that the total count of 1s is always an odd integer.

In digital hardware, 1D Parity is implemented using a balanced binary XOR tree, which computes the parity bit in O(log₂ n) gate delay levels. At the receiving node, the entire codeword (including the parity bit) is evaluated: P_rx = b₁ ⊕ b₂ ⊕ ... ⊕ bₙ ⊕ P. If P_rx = 0 for Even Parity (or 1 for Odd Parity), the frame passes verification; otherwise, a parity error is declared.

Detection Strength, Hamming Distance & Limits

Hamming distance = 2, odd error guarantees, and even cancellation:

The error detection capability of 1D Parity is governed by coding theory: appending a single parity bit establishes a minimum Hamming distance of d_min = 2 between valid codewords. According to the coding distance theorem, a code with minimum distance d_min can reliably detect up to s = d_min - 1 = 1 bit error. Consequently, 1D Parity guarantees 100% detection of all single-bit errors as well as any odd number of simultaneous bit flips (1, 3, 5, 7 bits).

However, 1D Parity is completely blind to any even number of bit errors (2, 4, 6 bits). When an even number of bits invert during transmission, the two bit flips mathematically cancel each other out in the XOR summation (1 ⊕ 1 = 0 ⊕ 0 = 0), producing an identical parity bit and resulting in undetected data corruption. Furthermore, 1D Parity provides zero error correction capability, requiring retransmission protocols when errors are flagged.

1D Parity Check: NS-2 Simulation & Protocols

Discrete-event duplex link modeling, trace log analysis, and asynchronous serial standards

NS-2 Channel Integration & Trace Analytics

Duplex link simulation and ErrorModel packet drop verification (ns2_parity.tr):

In our platform, the 1D Parity module is directly coupled with Network Simulator 2 via ns2/network_error_sim.tcl. The transmitter node (Node 0) formats the raw data vector (e.g., '11010010'), appends the computed parity bit ('0'), and packetizes the resulting 9-bit codeword into UDP/CBR packets. The packets are transmitted across a 2.0 Mbps duplex link with 10 ms delay toward the receiver sink (Node 1).

Channel noise is introduced using the NS-2 ErrorModel/Uniform module. When an error event corrupts a packet in transit, the event is recorded in the trace log (ns2_parity.tr). The receiver application parses the incoming packet, evaluates the parity bit, and immediately flags an 'Error Detected' condition upon bit mismatch. In our empirical trials, 100% of single-bit errors injected by NS-2 were caught and flagged at the receiver sink.

Industrial Protocols & Serial Framing Standards

UART microcontrollers, RS-232/485 serial communication, and SCSI bus validation:

Because 1D Parity incurs minimal bandwidth overhead (a single bit per frame) and requires trivial hardware logic, it remains the standard error-checking mechanism in low-speed, asynchronous serial communication protocols. In the universal RS-232, RS-422, and RS-485 serial communication standards (commonly utilized in UART microcontrollers and industrial automation), frames are formatted in the 8-N-1, 8-E-1 (Even Parity), or 8-O-1 (Odd Parity) formats.

While modern high-speed networks (such as Ethernet and Wi-Fi) have superseded simple parity with cyclic redundancy checks, 1D Parity continues to serve as an indispensable first-line validation check in SCSI bus transfers, PCI bus command lines, and microcontroller register transfers where processing power and silicon area are highly constrained.

● ALGORITHM 2 OF 5: PART A

2D Parity Matrix: Grid Architecture & Error Localization

Two-dimensional matrix parity for coordinate-based bit localization

Matrix Grid Structuring, LRC & VRC Formulations

Orthogonal parity constraints across M rows and N columns:

Two-Dimensional (2D) Parity Check, also known as Matrix Parity or Optimal Rectangular Code, overcomes the severe limitations of 1D Parity by organizing the raw binary message into a two-dimensional grid of M rows and N columns. In this architecture, two independent sets of parity bits are computed along orthogonal dimensions: Longitudinal Redundancy Check (LRC) bits for every horizontal row, and Vertical Redundancy Check (VRC) bits for every vertical column.

Specifically, each row i receives a row parity bit: R_i = ⊕ b_{i,j}. Each column j receives a column parity bit: C_j = ⊕ b_{i,j}. In addition, a corner parity bit is computed across all row parity bits: P_corner = ⊕ R_i. This creates an (M+1) × (N+1) codeword matrix with a total redundancy overhead of M + N + 1 bits, establishing two orthogonal parity constraints for every single data bit.

Geometric Intersection & Bit Localization

Spatial intersection of failing row and column syndrome vectors:

When the (M+1) × (N+1) frame is received, the destination node recalculates all row parities and all column parities, comparing them against the received parity bits to construct two syndrome vectors: a row syndrome S_R = (s_{r,1}, ..., s_{r,M}) and a column syndrome S_C = (s_{c,1}, ..., s_{c,N}).

If a single bit error occurs at matrix position (i, j), the parity check for row i fails (s_{r,i} = 1) and the parity check for column j fails (s_{c,j} = 1), while all other row and column parities evaluate to zero. The receiver identifies the unique geometric intersection (i, j) of the failing row and column, pinpointing the exact spatial coordinate of the corrupted bit without ambiguity.

● ALGORITHM 2 OF 5: PART B

2D Parity Matrix: Forward Error Correction & NS-2

Autonomous 1-bit repair, multi-bit burst detection, and trace verification

Forward Error Correction & Burst Detection

Autonomous 1-bit bit-flipping and multi-bit detection boundaries:

The defining technical breakthrough of 2D Parity over 1D Parity is its capability for Forward Error Correction (FEC) without retransmission. Once the coordinates of the failing intersection (i, j) are identified, the receiver simply inverts that specific bit (b[i][j] = ~b[i][j]), fully recovering the original data payload without requesting a retransmission from the sender.

In addition to single-bit correction, 2D Parity provides powerful multi-bit error detection: it detects 100% of all 2-bit errors (which cause two row failures or two column failures), 100% of all 3-bit errors, and 100% of all burst error corruptions of length up to N bits across a row. The only pattern that evades 2D Parity detection is a 4-bit error arranged in a perfect rectangle (i₁, j₁), (i₁, j₂), (i₂, j₁), (i₂, j₂), where each row and column contains an even number of flipped bits.

NS-2 Channel Integration & Trace Analytics

Discrete-event trace verification (ns2_parity2d.tr) and magnetic storage:

In our NS-2 simulation bridge, the serialized (M+1) × (N+1) matrix codeword is transmitted across the duplex link between Node 0 and Node 1. The discrete-event trace file (ns2_parity2d.tr) logs packet transmission timestamps, link propagation delays, and ErrorModel packet drop events.

When simulated channel noise inverts a bit in transit, the receiver reconstructs the matrix grid, highlights the intersecting row and column on the UI canvas, and automatically flips the corrupted bit back to its pristine value. In industrial practice, 2D Parity was widely deployed in 9-track magnetic tape storage drives and early telecommunication framing where burst errors along physical tracks were prevalent.

● ALGORITHM 3 OF 5: PART A

Hamming Code (n, k): Mathematical Foundations

Richard Hamming (1950) coding theory, power-of-two positioning, and linear block codes

Richard Hamming's Coding Theorem & Redundancy Rule

Mathematical bound 2ʳ ≥ k + r + 1 and power-of-two bit placement:

Invented by Richard W. Hamming at Bell Laboratories in 1950, Hamming Codes are a distinguished family of linear error-correcting block codes that achieve optimal single-error correction (SEC) with minimal redundancy overhead. For a block of k data bits, r redundant parity check bits are added to produce an n-bit codeword (n = k + r). The required number of check bits r is governed by Hamming's Rule: 2ʳ ≥ k + r + 1. In the foundational Hamming (7, 4) code, k = 4 data bits require r = 3 parity check bits (2³ = 8 ≥ 4 + 3 + 1 = 8).

Hamming's ingenious architectural rule dictates that parity check bits are assigned exclusively to bit positions that are powers of two: 1, 2, 4, 8, ..., 2^(r-1). The actual data bits occupy the remaining non-power-of-two indices (3, 5, 6, 7, 9, ...). This spatial distribution ensures that each bit's 1-indexed position can be uniquely expressed as a binary sum of power-of-two parity indices.

Orthogonal Bit Coverage & Parity-Check Matrix H

Subsets of codeword bits and linear parity equations over GF(2):

Each parity bit p_i located at index 2^(i-1) checks all bit positions whose binary representation contains a 1 at the i-th bit position. In Hamming (7, 4): parity bit p₁ (position 1 = 001₂) checks bits {1, 3, 5, 7}; parity bit p₂ (position 2 = 010₂) checks bits {2, 3, 6, 7}; and parity bit p₄ (position 4 = 100₂) checks bits {4, 5, 6, 7}.

This linear system can be elegantly expressed in matrix algebra over GF(2) using the generator matrix G and parity-check matrix H, such that any valid codeword c satisfies c · Hᵀ = 0. The minimum Hamming distance of the code is d_min = 3, enabling simultaneous detection of up to 2 bit errors and forward correction of any single-bit error.

● ALGORITHM 3 OF 5: PART B

Hamming Code: Syndrome Decoding, FEC & NS-2

Syndrome vector index mapping, server memory ECC RAM, and trace validation

Syndrome Calculation Vector & Autonomous Bit Recovery

Direct binary-to-decimal mapping of corrupted bit indices:

At the receiving destination, the syndrome vector S = (s₃, s₂, s₁)₂ is computed by evaluating the three linear parity-check equations over the received codeword: s₁ = b₁ ⊕ b₃ ⊕ b₅ ⊕ b₇, s₂ = b₂ ⊕ b₃ ⊕ b₆ ⊕ b₇, and s₃ = b₄ ⊕ b₅ ⊕ b₆ ⊕ b₇. If the received codeword is uncorrupted, all parity equations evaluate to zero, yielding syndrome S = 000₂.

If any single bit in the codeword is inverted during transit, the resulting binary syndrome S directly indicates the exact 1-indexed decimal position of the corrupted bit! For example, if bit 5 flips, s₁ = 1 and s₃ = 1 while s₂ = 0, producing syndrome S = 101₂ = 5. The receiver automatically executes b₅ = ~b₅, restoring the original data with 100% mathematical accuracy without retransmission.

NS-2 Channel Integration & Semiconductor ECC Memory

Server DRAM architectures, satellite links, and trace logs (ns2_hamming.tr):

In our NS-2 simulation bridge (ns2_hamming.tr), Hamming-encoded packets are transmitted across the duplex link between Node 0 and Node 1. The NS-2 ErrorModel drops and corrupts packets, simulating physical link noise. The receiver application captures the packet, computes the syndrome vector, and corrects the bit in real time.

In commercial computing, Hamming codes are ubiquitously deployed in server Error-Correcting Code (ECC) RAM, L1/L2/L3 processor caches, deep-space satellite telemetries, and RAID-2 disk architectures. By adding an overall parity bit, the code is extended to SEC-DED (Single Error Correction, Double Error Detection), providing comprehensive memory protection against cosmic ray soft-errors.

● ALGORITHM 4 OF 5: PART A

Internet Checksum: RFC 1071 Specifications

1's complement arithmetic, word segmentation, and end-around carry mechanics

RFC 1071 Standard Specification & 1's Complement

Software-oriented design for router forwarding engines and IP stacks:

The Internet Checksum is the foundational error-detection algorithm standardized in RFC 1071 and deployed across the core protocols of the Internet Protocol Suite, including the IPv4 header checksum, TCP segment integrity, and UDP datagram validation. The algorithm was intentionally designed for high-speed software execution inside network routers and host operating system kernels, where dedicated hardware division circuits are unavailable.

The algorithm segments the input byte stream into uniform k-bit words (standardized as 16-bit integers in IPv4 and TCP). These 16-bit words are summed sequentially using One's Complement Arithmetic. Unlike conventional two's complement addition, one's complement arithmetic treats signed and unsigned numbers such that negative values are bitwise inversions of positive values, establishing an arithmetic field where zero has two representations: positive zero (0x0000) and negative zero (0xFFFF).

End-Around Carry Wraparound & Checksum Inversion

Mathematical wraparound of high-order overflow carry bits:

During the sequential accumulation of 16-bit words, an addition will frequently generate an overflow carry bit beyond the 16th bit position (bit 17). In one's complement arithmetic, this overflow carry is not discarded; instead, it is wrapped around and added back into the least significant bit (LSB), a process designated as end-around carry. This ensures that carries from high-order bit positions contribute to lower-order bit positions, preserving arithmetic symmetry.

Once all 16-bit words have been accumulated into the running sum, the bitwise one's complement (NOT operation) of the final sum is calculated. This resulting 16-bit value is placed into the Checksum field of the packet header and transmitted alongside the payload.

● ALGORITHM 4 OF 5: PART B

Internet Checksum: Receiver Zero-Sum & NS-2

Receiver zero-check, algorithmic vulnerabilities, and packet drop modeling

Receiver Zero-Sum Verification & Efficiency

High-speed router verification and incremental TTL checksum updates:

At the receiving destination, the verification procedure is exceptionally elegant and computationally optimal for high-throughput router forwarding engines: the receiver sums all incoming 16-bit data words including the received checksum field using one's complement addition. If no bits were corrupted during transit, the resulting sum must evaluate to all 1-bits (0xFFFF), which inverts to 0x0000 (zero) upon complementation.

Any non-zero result alerts the receiving stack that transmission corruption occurred, prompting the immediate discard of the packet. Because one's complement addition is associative and commutative, intermediate routers can update the IPv4 header checksum incrementally when decrementing the Time-to-Live (TTL) field without recalculating the entire checksum from scratch: C' = C + m - m'.

Algorithmic Weaknesses & NS-2 Link Loss Modeling

Transposition blind spots, compensating errors, and trace logs (ns2_checksum.tr):

Despite its widespread adoption, the Internet Checksum possesses recognized algorithmic limitations: because addition is commutative, it is completely invariant to word transposition (swapping two 16-bit words leaves the sum unchanged). Furthermore, it cannot detect compensating bit errors where an increment in one word is mathematically cancelled by a decrement in another word. It also fails to detect the insertion or deletion of zero words (0x0000).

In our NS-2 simulation bridge, checksum-protected frames traverse the duplex link between Node 0 and Node 1 (ns2_checksum.tr). Corrupted packets that fail the receiver checksum validation trigger immediate link drops, modeling the exact behavior of IP routers encountering corrupted transport headers.

● ALGORITHM 5 OF 5: PART A

CRC Modulo-2 Division: Galois Field GF(2) Theory

Algebraic coding theory over GF(2), polynomial arithmetic, and Frame Check Sequence generation

Algebraic Foundations & Polynomial Ring Arithmetic

Galois Field GF(2) coefficients and XOR addition without borrow:

Cyclic Redundancy Check (CRC) is the most powerful, mathematically rigorous, and widely deployed error-detection mechanism in modern computer networking, serving as the mandatory standard for Ethernet (IEEE 802.3), Wi-Fi (IEEE 802.11), USB, SATA, and cellular wireless links. CRC treats binary data sequences as algebraic polynomials whose coefficients belong to the Galois Field of two elements, GF(2).

In GF(2) polynomial arithmetic, addition and subtraction are identical and equivalent to the bitwise Exclusive-OR (XOR) operation performed without carries or borrows. For example, 1 + 1 = 0, 1 + 0 = 1, and 0 + 0 = 0. A binary data sequence such as '1101001' is represented as the polynomial D(x) = x⁶ + x⁵ + x³ + 1. The sender and receiver agree in advance upon a generator polynomial G(x) of degree r, where the most significant bit and least significant bit are always 1.

Sender Encoding Algorithm & Frame Check Sequence (FCS)

Modulo-2 polynomial long division and transmitted codeword construction:

The sender encoding procedure proceeds in four formal algebraic steps: First, the n-bit data polynomial D(x) is multiplied by xʳ, effectively shifting the data left by r bit positions and appending r zero bits: D(x) · xʳ. Second, D(x) · xʳ is divided by the generator polynomial G(x) using Modulo-2 polynomial long division.

Third, the resulting r-bit remainder polynomial R(x) = rem(D(x) · xʳ / G(x)) constitutes the Frame Check Sequence (FCS). Fourth, the FCS is added to the shifted data polynomial to construct the transmitted codeword: T(x) = D(x) · xʳ ⊕ R(x). By polynomial algebra, T(x) is mathematically guaranteed to be exactly divisible by G(x) without remainder: T(x) mod G(x) ≡ 0.

● ALGORITHM 5 OF 5: PART B

CRC Modulo-2: Detection Proofs & NS-2

Mathematical error detection proofs, industry standard polynomials, and link trace analysis

Comprehensive Mathematical Error Detection Proofs

Algebraic proofs for single, double, odd, and burst error detection:

The algebraic properties of CRC provide extraordinary detection power: Let the transmitted codeword be T(x) and the received codeword be T(x) ⊕ E(x), where E(x) is the error polynomial. The receiver divides by G(x), evaluating (T(x) ⊕ E(x)) / G(x) = E(x) / G(x). An error is undetected if and only if E(x) is exactly divisible by G(x).

1. Single-bit errors: E(x) = xⁱ. Since G(x) has at least two non-zero terms (xʳ + ... + 1), it cannot divide xⁱ, guaranteeing 100% single-bit detection.
2. Double-bit errors: E(x) = xⁱ + xʲ = xʲ(xⁱ⁻ʲ + 1). If G(x) does not divide (xᵏ + 1) for any k ≤ frame length, 100% of double-bit errors are detected.
3. Odd-numbered errors: If G(x) contains (x+1) as a factor, it catches 100% of all odd-numbered errors.
4. Burst errors: Catches 100% of all burst error corruptions of length ≤ r bits.

Industry Standard Generators & NS-2 Trace Integration

Ethernet IEEE 802.3, hardware LFSR circuits, and NS-2 drops (ns2_crc.tr):

Our platform implements key industry generator polynomials: CRC-4 ITU (x⁴ + x + 1), CRC-8 ATM, CRC-16-IBM, CRC-CCITT, and CRC-32 (IEEE 802.3 Ethernet standard: x³² + x²⁶ + x²³ + ... + 1). While software CRC requires O(n · r) operations, hardware implementations execute at wire speed (O(1) cycle latency) using Linear Feedback Shift Registers (LFSR).

In our NS-2 simulation (ns2_crc.tr), CRC-encoded frames traverse the simulated duplex link under varying ErrorModel loss rates. Corrupted frames reliably trigger non-zero syndrome remainders and register drop events in the NS-2 trace, modeling realistic Ethernet frame discards.

● CHANNEL SIMULATION ENGINE: PART A

NS-2 Architecture: OTcl Scripting & Channel Modeling

Coupling physical link discrete-event simulation with Data Link Layer error control

Dual-Language Architecture & OTcl Topology Scripting

C++ discrete-event scheduler coupled with Object Tcl configuration scripts:

Network Simulator 2 (NS-2) is an industry-standard, object-oriented discrete-event network simulator widely utilized in telecommunication research to model network protocol dynamics, routing algorithms, and physical channel transmission impairments. NS-2 employs a dual-language architecture: the core simulation engine and packet scheduler are written in C++ for maximum computational throughput, while simulation topology scripts, agent configurations, and event schedules are authored in Object Tcl (OTcl).

In our project, the physical channel is configured in ns2/network_error_sim.tcl. The simulation creates a point-to-point network topology consisting of a source node (Node 0) and a destination sink node (Node 1). Node 0 is configured with a UDP agent connected to a Constant Bit Rate (CBR) traffic generator transmitting 64-byte packets. Node 1 is equipped with an Agent/Null sink. The two nodes are connected via a full-duplex link configured with a bandwidth of 2.0 Mbps, a propagation delay of 10 ms, and a DropTail queue discipline.

Physical Noise Injection & ErrorModel Loss Mechanics

Stochastic uniform packet corruption and drop-target redirection:

To authentically simulate noisy physical transmission channels, the NS-2 ErrorModel/Uniform module is inserted directly into the duplex link between Node 0 and Node 1. The ErrorModel applies a configurable statistical packet loss rate, causing packets to be dropped or corrupted during transit. Dropped packets are redirected to an Agent/Null drop-target, capturing realistic channel packet drop behavior.

The simulation script schedules packet transmissions, initiates CBR traffic flows at t = 0.5 s, and terminates the simulation run at t = 4.5 s. Output event traces are flushed directly to standard .tr files and Network Animator (.nam) visualization files, allowing comprehensive inspection of packet queues, link traversal latencies, and packet drop events.

● CHANNEL SIMULATION ENGINE: PART B

NS-2 Trace Analytics: 12-Column Records & PER

Event record schema, Packet Error Rate calculation, and WSL execution bridge

12-Column NS-2 Event Record Architecture

Microsecond event log schema across simulated network links:

As packets traverse the simulated link, NS-2 outputs granular event records to standard trace files (.tr). Each line in the trace file contains twelve whitespace-delimited columns that completely characterize a discrete network event: 1. Event Type: '+' (Enqueue), '-' (Dequeue/Transmit), 'r' (Receive), 'd' (Drop). 2. Event Timestamp: Simulation time in seconds with microsecond precision. 3. Source Node ID: Node where event occurred (e.g., 0). 4. Destination Node ID: Intended destination node (e.g., 1).

Columns 5 to 12 record: 5. Packet Name: Protocol type (cbr / UDP), 6. Packet Size: in bytes (64), 7. Flags: protocol flags, 8. Flow ID: flow identifier, 9. Source Address: (0.0), 10. Destination Address: (1.0), 11. Sequence Number: sequential index, and 12. Unique Packet ID: assigned by scheduler.

Python-to-NS-2 Bridge & Live PER Analytics

Subprocess execution, regex parsing, and live dashboard metrics:

Our Python simulation bridge (modules/ns2_bridge.py) automates the execution of NS-2 inside Windows Subsystem for Linux (WSL) and parses the 12-column event records in real time. The bridge extracts total transmitted packets (N_tx), total successfully received packets (N_rx), and total dropped packets (N_drop).

The Packet Error Rate (PER) is computed mathematically as: PER = (N_drop / (N_rx + N_drop)) × 100%. The parsed metrics, transmission latencies, and drop event breakdowns are streamed directly to the web dashboard and desktop GUI, providing transparent verification of physical channel noise.

Multi-Dimensional Technical Trade-Off Analysis

A comprehensive engineering evaluation of error control mechanisms requires balancing four competing design constraints: transmission bandwidth overhead, computational complexity, error detection strength, and forward error correction capability. 1D Parity offers the absolute lowest bandwidth overhead (1 bit per codeword) and simplest hardware implementation (O(n) XOR gates), but provides no error correction and fails to detect even numbers of bit flips. 2D Parity introduces moderate overhead (M + N + 1 bits) but achieves single-bit forward error correction through orthogonal grid localization. Hamming Code provides optimal single-error correction (SEC) with logarithmic parity overhead (ceil(log2(n+k+1))), making it ideal for hardware-accelerated memory architectures.

The Internet Checksum requires a constant 16-bit overhead per packet and operates via simple 1's complement arithmetic (O(n) time), making it exceptionally lightweight for software execution in operating system IP stacks, though it is vulnerable to transposed and compensating bit errors. Cyclic Redundancy Check (CRC) represents the pinnacle of error detection power, guaranteeing 100% detection of all single-bit, double-bit, odd-bit, and burst errors up to r bits. Although software CRC division requires O(n · r) operations, hardware implementations execute at wire speed (O(1) cycle latency) using Linear Feedback Shift Registers (LFSR). In industry, these techniques are deployed across standard protocol layers: 1D Parity in asynchronous RS-232 serial links, 2D Parity in magnetic tape storage, Hamming Code in ECC RAM and RAID-2, Checksum in IPv4/TCP/UDP, and CRC in Ethernet IEEE 802.3 and Wi-Fi.

1. Key Accomplishments & Architecture

Project engineering deliverables:

The Interactive Network Error Detection & Correction Simulator was developed using an enterprise-grade multi-platform architecture designed for accessibility, academic demonstrations, and research experimentation. Network Simulator 2 (NS-2) runs natively or via Windows Subsystem for Linux (WSL), bridged via real-time subprocess execution. The platform delivers an unprecedented level of interactive control: users can toggle bits at will, inject burst noise, configure NS-2 link parameters, and observe mathematical syndrome calculations updating instantaneously. The software architecture is cleanly separated into modular components, ensuring zero external dependencies for desktop execution and providing full REST API endpoints for web-based experimentation.
